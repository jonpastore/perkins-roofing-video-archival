## Governing rule

**Existing production capabilities are PRESERVED BY DEFAULT.** A redesign, cleaner hierarchy, prototype omission, or information-architecture change is never permission to remove functionality. Any removal, deprecation, material reduction, or behavioral change must be explicitly recorded here and approved by the product owner.

`PROPOSE DEPRECATION` appears nowhere in this matrix. The prototype demonstrates a direction, not the complete product.

## Selective prototype requirements

The current command-center prototype intentionally demonstrates only urgent revenue work, scoped portfolio visibility, mobile action flow, and representative asynchronous/error states. It does **not** prototype the capabilities marked `No` above.

Two additional mock-data prototypes are warranted because they answer consequential design questions rather than repeat an established pattern:

1. **Estimate workspace:** prove that complex measurement/pricing/provenance and multi-step quote work can remain efficient inside the customer/property model.
2. **Platform Operations:** prove that readiness, per-integration state, remediation, diagnostics and restricted data density remain discoverable without polluting branch Today.

All other rows map to an established target workspace or pattern and do not require a redundant mockup at this phase.

## Future implementation-plan traceability rule

Every approved implementation work package must cite the relevant matrix rows and prove:

```text
CURRENT CAPABILITY → TARGET EXPERIENCE → REPOSITORY WORK PACKAGE
→ ACCEPTANCE CRITERIA → TEST COVERAGE
```

An implementation plan is incomplete if a current capability lacks a disposition or a testable target behavior.

## GHL implementation boundary and CallRail scope resolution

GHL is an approved operating dependency, already in use outside this app. Its target topology is one corporate Tim account/location plus one branch sub-account/location per branch. The app has not yet implemented its use, so a technical discovery work item must establish API/webhook scope, event ordering/idempotency, contact matching, stage/calendar ownership, error/retry behavior, server authorization, connection health and server-side credential references before implementation planning. This is a planning gate, not a claim that the app has verified an integration.

CallRail is not approved. It is neither preserved as an implemented feature nor proposed for deprecation; it simply has no approved target scope. No code, configuration or credential model should be planned for it until the product owner explicitly approves it.
