PHASE 1 — WIND NOISE
═══════════════════════════════════════════════════════════════════════════════

WHAT EXISTS (do not rebuild it — verify each claim before you touch anything):
  core/audio_enhance.py       build_enhance_filter / build_enhance_cmd
                              afftdn=nf=-25 + acompressor + loudnorm(-14 LUFS)
  core/render_spec.py:268     audio_enhance: bool = False
  jobs/render_job.py:366      applies it, non-fatal on exception
  api/routes/clips.py:874     exposes it

THE GAP: that afftdn value is tuned by its own comment for "HVAC/room noise" — indoor and
stationary. Tim shoots outdoors on a phone. Wind is LOW-FREQUENCY and NON-STATIONARY; nothing
in the chain high-passes, and afftdn adapts poorly to it.

DO:
  1. Add a `wind: bool = False` option to build_enhance_filter/build_enhance_cmd that prepends a
     high-pass and adjusts the denoiser for outdoor use, e.g.
         highpass=f=90, afftdn=nf=-20, acompressor=..., loudnorm=...
     Tune the exact values against the real clip in step 4 — do not just accept these numbers.
  2. The DEFAULT PATH MUST STAY BYTE-IDENTICAL. Add a test asserting the wind=False filter
     string is exactly what it is today, so this cannot regress existing renders.
  3. Thread `wind` through render_spec -> render_job -> api/routes/clips.py, mirroring exactly
     how `audio_enhance` already flows. Grep the READER, not the key — this repo's recurring
     defect is config with no reader (see CLAUDE.md and §1).
  4. Find a REAL Tim clip with wind. Check the archived GCS MP4s / existing videos in the DB
     first; if nothing suitable exists, say so and ask rather than fabricating a test file.

DELIBERATELY NOT DOING: DeepFilterNet3. It is a new dependency plus model weights. Both reviewers
said high-pass + low-end cleanup is the bulk of the win on wind specifically. If step 4 proves it
insufficient, STOP and report — do not add the dependency unilaterally.

A/B ARTIFACT (required):
  - Two playable files from the SAME source clip: `wind_before.mp4` and `wind_after.mp4`
  - Put them somewhere Jon can open them, and print the paths
  - Measured, not asserted: integrated LUFS before/after (ffmpeg loudnorm print_format=json),
    and a one-line description of what changed in the low end
  - Say plainly if it does NOT sound better. A negative result is a real result.

PHASE 2 — ADDRESS / PII REDACTION
═══════════════════════════════════════════════════════════════════════════════

WHY: OpusClip has no PII redaction at all (verified both engines). Tim films clients' houses;
street numbers are visible. CompanyCam already burns GPS into photo pixels — same instinct.

WHAT EXISTS: nothing visual. core/censor.py mutes AUDIO for flagged words.
core/photo_privacy.py CROPS stills. Neither blurs video.

READ core/photo_privacy.py FIRST for this project's privacy doctrine:
  "The stamp is CUT, not blurred. A blur is a guess about how much entropy is left in the
   pixels; a crop removes them."
That is why Phase 2 is an OPERATOR-MARKED region, not OCR auto-detection: an operator-confirmed
box is not a guess.

DO:
  1. New core/video_redact.py — PURE, no I/O, no subprocess (same split as core/audio_enhance.py).
     A function turning redaction regions into an ffmpeg filter string:
         regions: [{x, y, w, h, t0, t1}, ...]  ->  filter using enable='between(t,t0,t1)'
     PIXELATE, not inpaint, and not a soft blur. A visible redaction is legally defensible;
     inpainting alters the footage and costs GPU-minutes per video-minute.
  2. Validate inputs at the boundary: negative/zero w/h, t1 <= t0, regions outside frame bounds,
     empty list. This is a privacy path — do not simplify the validation away.
  3. Wire it the same way audio_enhance is wired: render_spec field -> render_job -> clips API.
  4. Tests in core/ (R1 applies): filter-string assertions plus ONE behavioural check that
     actually runs ffmpeg on a small generated clip and confirms the pixels in the region changed
     and the pixels outside it did not.

DEFERRED, do not build: OCR auto-detection (PaddleOCR/EasyOCR + tracking). Phase 2 proves the
render path; auto-detect comes later once we know the real shot patterns.

A/B ARTIFACT (required):
  - `redact_before.mp4` and `redact_after.mp4` from the same clip, with a house number or address
    visibly pixelated in the after and nothing else changed
  - Print the paths. A still frame from each (PNG) is also fine and probably easier to eyeball.
